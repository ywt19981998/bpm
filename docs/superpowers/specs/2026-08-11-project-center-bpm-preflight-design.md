# 选题项目中心与 BPM 填报核对设计

## 目标

将现有的“策划报告”“作译者维护”和“BPM 选题填报”串成以每个选题为单位的持久项目。用户上传文件或生成报告后，可以关闭页面、换浏览器或换电脑继续处理；发起 BPM 任务前先核对实际将写入的字段，并以 BPM 工作列表中可查到的暂存选题作为成功依据。

## 范围

本次包含：

- 每个用户私有的选题项目中心。
- 选题申报表、已确认策划报告和导出文件的服务端保存。
- 报告正文、评分、BPM 字段和作译者资料的服务端持久化。
- 项目阶段状态、最近操作时间和对应 BPM 任务。
- BPM 填报前的字段核对表和阻断性校验。
- BPM 任务的阶段化日志和真实成功验证。
- 对现有浏览器草稿的一次性安全迁移。

本次不包含：

- 管理员后台、跨用户项目共享和多人协同编辑。
- 审批流、消息通知、手机端应用或公网部署。
- 数字教材合同制作和合同 BPM 填报。合同模块后续复用本次的项目、文件和任务边界。
- 任意格式文件的通用网盘能力。

## 用户流程

### 新建并生成报告

1. 用户登录后默认进入“项目中心”。
2. 点击“新建选题”并上传选题申报表。
3. 服务端先创建项目并保存原文件，再执行解析和模型生成。
4. 用户在现有报告编辑页确认六段正文和评分，修改持续自动保存到当前项目。
5. 六段全部确认后，项目状态变为“报告已确认”，可导出 DOCX 或进入 BPM 核对。

### 快速导入已有材料

1. 用户在 BPM 页同时上传申报表和已确认策划报告。
2. 系统创建项目，保存两个原文件，并把解析后的报告和 BPM 数据写入项目。
3. 项目直接进入“待核对”，不再调用大模型重新生成全文。

### BPM 核对与任务

1. 用户从项目进入 BPM 页，页面按字段显示拟写入值、数据来源和校验状态。
2. 阻断性字段缺失时，“填报选题”按钮不可用；可选字段缺失时仅提示。
3. 用户可先单独发起作译者维护，也可跳过已存在的作者。
4. 选题填报任务绑定当前项目，项目页实时显示队列、执行、失败或成功状态。
5. 只有在 BPM 工作列表重新找到该书名或单据号后，任务才标记为成功。

## 页面设计

### 项目中心

项目中心使用紧凑表格，不使用大量卡片。列包含：

- 选题名称。
- 第一作者。
- 责任编辑。
- 报告状态。
- 作译者状态。
- BPM 状态。
- 最近更新时间。
- 操作菜单：继续处理、导出报告、归档。

页面顶部只保留搜索、状态筛选和“新建选题”。默认显示未归档项目，按最近更新倒序。空页仅引导上传申报表，不预置示例选题。

### 项目工作区

打开项目后，顶部始终显示书名、当前阶段和最近保存时间。现有“策划报告”和“BPM 填报”作为项目内两个工作页保留，不重写已稳定的编辑和队列逻辑。未选中项目时，两个入口引导用户先新建或打开项目。

### BPM 字段核对

核对表列包含“字段”“将写入的值”“来源”“状态”。来源统一为：申报表、策划报告、固定规则、模型判断、用户修改、BPM 账号身份。状态统一为：已就绪、待确认、缺失阻断、可选缺失。修改后立即写回当前项目，不只修改当次任务请求。

## 数据模型

SQLite 使用新的迁移版本，不删除现有数据。

### projects

- `id`：UUID 字符串主键。
- `user_id`：关联项目所属用户，所有读写必须同时限制当前用户。
- `title`、`author_name`、`editor_name`：列表查询需要的摘要字段。
- `report_status`：`empty`、`draft`、`confirmed`。
- `author_status`：`unknown`、`ready`、`queued`、`running`、`succeeded`、`failed`。
- `bpm_status`：`not_ready`、`ready`、`queued`、`running`、`succeeded`、`failed`。
- `state_json`：报告六段、评分、`bpmTopic`、`authorMaintenance`和字段来源元数据。
- `version`：乐观锁版本，每次成功保存递增。
- `created_at`、`updated_at`、`archived_at`。

状态字段只存取值明确的阶段结果，不使用一个含义模糊的“项目已完成”。

### project_files

- `id`：UUID 字符串主键。
- `project_id`：关联项目。
- `kind`：`application`、`confirmed_report`、`exported_report`、`bpm_evidence`。
- `original_name`：原始上传或导出名称，仅用于显示。
- `storage_path`：数据目录内的相对路径，禁止存绝对路径。
- `sha256`、`size_bytes`、`created_at`。

文件存储在 `data/projects/<user_id>/<project_id>/`，磁盘名称使用文件 UUID，不直接使用用户上传的文件名。

### project_revisions

- `id`、`project_id`、`version`、`snapshot_json`、`reason`、`created_at`。

只在导入文件、报告全部确认、BPM 任务发起前和用户手动保存时建立快照，不对每次输入产生版本。

### jobs 扩展

向现有 `jobs` 表增加可空 `project_id`，新的作译者和选题填报任务必须绑定项目。旧任务保留为未关联历史记录，不伪造归属。

## 文件与并发边界

- 仅接受 `.docx`，同时校验 ZIP/DOCX 结构，不只信任扩展名。
- 单个文件默认不超过 20 MB，超限返回可理解错误。
- 文件先写临时路径，验证成功后原子替换；数据库失败时删除未关联文件。
- 更新项目时客户端提交它最后读取的 `version`。版本不匹配返回 409，页面提示刷新，不静默覆盖另一个页签的更改。
- 归档只写 `archived_at`，不删除文件。本次不提供永久删除入口。

## API 设计

- `GET /api/projects`：返回当前用户的项目摘要，支持状态、归档和关键词过滤。
- `POST /api/projects`：创建空项目或由申报表创建项目。
- `GET /api/projects/<id>`：返回当前用户的完整项目状态和文件摘要。
- `PUT /api/projects/<id>`：根据 `version` 更新项目内容。
- `POST /api/projects/<id>/files`：上传并解析指定类型文件。
- `POST /api/projects/import`：由申报表和已确认报告一次性创建项目。
- `POST /api/projects/<id>/revisions`：建立显式项目快照。
- `POST /api/projects/<id>/archive`：归档项目。
- `GET /api/projects/<id>/preflight`：返回 BPM 字段核对结果。
- `GET /api/projects/<id>/files/<file_id>`：在权限校验后下载文件。

现有生成、导入、导出和 BPM 任务接口在过渡期保留。前端逐步改为携带 `projectId`；服务端从项目取得可信数据，不以客户端临时拼装的姓名、BPM 凭据或项目所属为准。

## 状态和成功定义

### 报告状态

- `empty`：尚无可编辑报告。
- `draft`：已生成或导入，但六段未全部确认。
- `confirmed`：六段全部确认且评分合法。

### BPM 任务里程碑

- `login_verified`：已登录并读到 BPM 当前用户身份。
- `topic_form_opened`：已打开新建选题表单。
- `topic_draft_saved`：已点击 BPM 的“暂存”并取得书名或单据号。
- `cost_estimate_saved`：成本估算子表已保存。
- `worklist_verified`：刷新工作列表后找到对应书名或单据号。

`jobs.status = succeeded` 只能在 `worklist_verified` 后写入。任意中间步骤失败时，项目保留最后完成里程碑、脱敏错误、运行记录目录和可用截图，页面明确显示失败在哪一步。

## 浏览器草稿迁移

- 登录后如果发现当前用户的 `phei-report-draft-v3` 且具有报告内容，显示一次“恢复为项目”提示。
- 用户确认后创建项目；服务端成功返回项目 ID 后才删除旧草稿。
- 由于浏览器旧草稿不包含原始上传文件，迁移项目显示“源文件未保存”，但不阻断继续编辑或导出报告。
- 已迁移标记与项目 ID 一起保存，避免刷新页面重复建项目。

## 错误处理

- 项目或文件不属于当前用户时统一返回 404，不泄露其他用户是否存在该资源。
- 文件无效、超限或解析失败时，项目保留在可恢复状态，不伪造报告或 BPM 数据。
- 自动保存失败时顶部显示“未保存”，保留本地临时缓存，用户可重试，不将失败显示成已保存。
- 并发版本冲突时停止自动保存，提供“重新载入”和“保留当前内容为新版本”，不直接覆盖。
- BPM 失败不自动无限重试。用户查看阶段和截图后手动重试，重试创建新任务并保留原记录。

## 测试与验收

### 自动测试

- 项目创建、列表、更新、归档和用户隔离。
- 项目乐观锁冲突和修订快照。
- DOCX 结构、大小和存储路径校验，包括路径穿越攻击。
- 项目 API 的未登录拒绝和跨用户 404。
- 报告状态和 BPM 核对阻断规则。
- 旧浏览器草稿只迁移一次，失败时不删除。
- BPM 任务绑定项目，且只有 `worklist_verified` 后才成功。
- 现有认证、报告生成、DOCX 导出、作译者和 BPM 脚本回归测试继续通过。

### 手工验收

1. 用户 A 创建项目并生成报告，关闭浏览器后重新登录，能继续上次内容。
2. 用户 B 无法查看、下载或修改用户 A 的项目。
3. 快速导入两个 DOCX 后，项目出现在列表并直接进入 BPM 核对。
4. 修改任意报告段落后刷新，内容和确认状态保留。
5. BPM 必填字段缺失时无法入队；补齐后可以入队。
6. BPM 脚本中途失败时，项目显示确切失败阶段和原任务记录。
7. BPM 工作列表可查到书名或单据号后，项目才显示“暂存成功”。

## 实施分段

1. 项目数据库、文件存储和 API。
2. 紧凑项目列表、项目工作区和草稿迁移。
3. 现有报告生成、快速导入、导出和 BPM 任务绑定项目。
4. BPM 字段核对、阻断校验和阶段化成功验证。
5. 全量回归、桌面和移动端视觉检查、服务器备份说明和 Git 版本标记。
