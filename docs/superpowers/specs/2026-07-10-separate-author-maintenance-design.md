# 作译者维护与选题填报拆分设计

## 背景

当前网页只有一个“加入队列”动作，后台脚本会先新增作译者，再创建选题申报。作译者可能已经存在，也可能因为字段或 BPM 页面异常而失败；这会阻断本来可以独立完成的选题暂存。

本次改造把“新增作译者”和“填报选题”拆成两个由用户明确触发的任务。模型配置和现有 API Key 保持不变。

## 目标

- 用户可单独新增作译者，不创建选题申报。
- 用户可单独填报选题，不新增或修改作译者。
- 作者已存在时，用户只需点击“填报选题”。
- 两类任务分别显示状态、日志和结果，任一任务失败都不影响另一类任务。
- 保留现有申报表解析、作者简介生成、选题评分、成本估算和暂存验证能力。

## 页面设计

BPM 填报页面顶部提供两个明确动作：

- 主按钮“填报选题”：创建并暂存选题申报，随后填写评分和成本估算。
- 次按钮“新增作译者”：只把当前已提取的作译者资料保存到 BPM 作译者库。

两个按钮共用现有 BPM 地址、账号、姓名和密码输入框。按钮点击后均显示确认提示，确认文字应包含任务类型、书名或作者姓名，避免误操作。

作译者状态条继续显示作者姓名、工作单位和简介准备状态，但文案改为“可单独新增至 BPM 作译者库”，不再暗示选题填报会自动新增作译者。

任务日志中的每条任务增加类型标识：

- 选题填报
- 作译者维护

选题填报继续要求一至六部分完整并已确认。新增作译者不要求六段报告全部确认，但要求有效作者姓名和非空作者简介。

## 后台与脚本边界

后台提供两条独立任务入口：

- 选题任务：构建选题数据并调用脚本的选题暂存命令。
- 作译者任务：构建作译者数据并调用脚本的作译者保存命令。

Playwright 脚本拆成两个可独立执行的命令：

- `submit-topic <topic.json>`：登录 BPM、填写选题、点击暂存、重新打开草稿、保存评分和成本估算、验证待办标题。该命令不得调用任何新增作译者函数。
- `submit-author <topic.json>`：登录 BPM、进入作译者信息维护、新增作译者、保存并返回作者姓名和截图。该命令不得打开选题申报页面。

为兼容现有调试命令，可暂时保留旧 `submit` 作为 `submit-topic` 的别名，但其行为必须改成仅填报选题。

## 数据流

申报表解析和报告生成仍负责产生 `bpmTopic.authorMaintenance`。该对象可同时存在于当前草稿中，但只有“新增作译者”任务会消费它。

“填报选题”任务使用选题正文、分类、评分和成本字段。主选题表中的主要作译者编号和主要作译者姓名继续保持空白，供用户之后在 BPM 作者库中手工关联。

“新增作译者”任务使用作者姓名、单位、联系方式、经历和作者简介。除姓名和作者简介外，缺失字段继续按现有规则填入全角空格，以满足 BPM 保存要求。

## 状态与错误处理

两类任务分别进入后台串行队列，避免同时操作同一个 BPM 账号。任务对象记录 `type`、`title`、`status`、`logs`、`result` 和 `error`。

选题任务只有在待办列表验证到书名和编号后才标记完成。作译者任务只有在点击保存后没有 BPM 错误提示，并取得可验证的保存结果或成功页面状态时才标记完成；不能仅以脚本退出码为成功依据。

失败任务保留输入 JSON、标准输出、错误输出和截图到现有 `output/bpm-runs/` 目录。网页错误信息应指出失败的是“选题填报”还是“作译者维护”。

本次不自动查询作者是否已存在，也不自动跳过重复作者。是否点击“新增作译者”由用户判断，避免姓名相同但实际为不同人员时误判。

## 测试与验收

- 单元测试确认 `submit-topic` 不调用 `saveAuthorMaintenance`。
- 单元测试确认 `submit-author` 不调用 `openTopicPopup`、评分或成本估算流程。
- 后台接口测试确认两种任务使用不同类型和日志文案。
- 页面测试确认两个按钮发送到不同接口，并执行各自的前置校验。
- 回归测试确认选题暂存、评分、成本估算和待办验证保持可用。
- 手工验收场景一：作者已存在，只点击“填报选题”，BPM 中出现完整选题草稿且不新增作者。
- 手工验收场景二：新作者，只点击“新增作译者”，BPM 作者库保存成功且不创建选题流程。
- 手工验收场景三：先新增作者、再填报选题，两条任务日志和结果互不覆盖。

## 非目标

- 本次不修改模型 URL、模型名称或 API Key 管理方式。
- 本次不实现作者库自动查重或自动关联主要作译者。
- 本次不改变策划报告生成、编辑和 DOCX 导出规则。
