# 大模型作者姓名识别设计

## 背景与根因

申报表中的作者表头可能使用字符间空格，例如“姓　名”。DOCX 抽取后该表头变为“姓 名”，而现有作者识别依赖“姓名”“作者姓名”等固定字段名，因此无法取到相邻值“陈凯翔”。工作单位等其他字段仍能成功抽取，所以页面会出现“作译者：待识别”但显示正确工作单位的情况。

本次改造不再通过字段名模式决定作者姓名。作者姓名由大模型读取申报表表格上下文后以结构化字段返回，规则代码只负责验证模型结果是否符合可保存的姓名格式。

## 目标

- “姓　名 / 陈凯翔”等带空格、换行或非标准表头能够被识别。
- 正常“生成全部”复用现有报告生成模型调用，不增加模型请求次数。
- “快速填 BPM”使用一次轻量模型请求识别作者姓名。
- 模型不能确定作者姓名时返回空字符串，不从作者简介或无关人名中猜测。
- 保存模型判断所依据的简短证据，便于定位错误识别。
- 不改变现有作者简介生成、BPM 作译者维护和选题填报拆分规则。

## 模型输入

新增 `author_source_context`，来源为申报表的原始表格行，而不是预先筛选后的固定字段字典。每行保留表格顺序和单元格文本，使模型能够理解“姓 名”与右侧“陈凯翔”的邻接关系。

发送模型前执行隐私过滤：身份证号、电话、邮箱、传真、详细地址和邮编所在行不进入作者姓名上下文。该过滤仅用于防止敏感信息进入模型，不参与作者姓名判断。单元格文本限制长度，表格行限制数量，避免提示词过大。

模型同时接收明确约束：

- 只从具有姓名语义的独立表格字段或明确作者名单中提取第一作者。
- 不把责任编辑、联系人、学校名称、单位名称、职称或简介中提到的其他人当作作者。
- 输出姓名原文，不附加“教授”“主编”等职称。
- 无法确定时输出空字符串。

## 正常生成流程

正常“生成全部”继续只调用一次报告生成模型。报告提示词新增 `author_source_context`，输出结构扩展为：

```json
{
  "authorMaintenance": {
    "name": "陈凯翔",
    "nameEvidence": "表格行：姓 名 | 陈凯翔",
    "bio": "作者简介"
  }
}
```

`normalize_generated()` 保留 `name`、`nameEvidence` 和 `bio`。`build_author_maintenance()` 只采用模型输出的 `name`，不再调用固定字段名识别函数作为作者姓名来源。`clean_person_name()` 仅作为模型输出的格式校验：允许 2-8 个中文字符和中间点，剥离模型偶尔附带的“姓名：”前缀；校验失败则姓名为空。

## 快速导入流程

“快速填 BPM”没有报告生成模型调用，因此增加一次轻量作者识别请求：

1. 前端随申报表和策划报告一起提交当前模型 URL、模型名称和临时 API Key。
2. 后端从申报表构建同样的 `author_source_context`。
3. 调用模型，仅返回 `name` 和 `nameEvidence`。
4. 将模型姓名与策划报告中的作者简介合并到 `authorMaintenance`。
5. 构建 BPM 数据并进入现有独立作译者/选题流程。

临时 API Key 为空时继续使用服务器默认 Key。模型调用失败或返回无效 JSON 时，快速导入返回明确错误，不静默退回字段模式匹配。

## 页面反馈

识别成功时继续显示“作译者：姓名”和工作单位。识别失败时显示“作译者：待识别”，同时在导入或生成错误中说明模型没有从申报表确认作者姓名。

作者识别证据只用于诊断和日志，不作为 BPM 填报字段，也不在页面展示敏感内容。

## 测试与验收

- 测试 `author_source_context` 保留“姓 名 | 陈凯翔”的相邻关系。
- 测试敏感联系方式和身份证行不会进入模型上下文。
- 测试正常生成的 `authorMaintenance.name` 能进入 BPM 作译者数据。
- 测试正常生成不再以固定字段名函数作为作者姓名来源。
- 测试快速导入会传递模型配置并调用轻量作者识别。
- 测试模型返回空姓名时不会把“自由职业”或简介中的其他人名当作作者。
- 使用包含“姓　名 / 陈凯翔”的申报表完成一次生成或等价模型响应测试，页面应显示“作译者：陈凯翔”。

## 非目标

- 本次不让模型改写身份证、电话、邮箱等联系方式。
- 本次不自动判断 BPM 作者库中是否已有同名作者。
- 本次不改变作者简介的官网检索和摘要规则。
- 本次不修改模型 URL、模型名称和 API Key 的默认配置。
